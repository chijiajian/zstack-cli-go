## Blocking findings

1. **5.2 — package metadata can lie about the binary.** [Build-Package.ps1](../powershell/packaging/Build-Package.ps1) checks the PE architecture, then copies `-CliVersion`/`-CliCommit` and capability names from caller input/static source status. A local build with the current Windows binary and `-CliVersion wrong -CliCommit wrong` succeeded. The module rejects the package on first command, but AC #3 requires the build itself to fail for a mismatch. Probe the supplied binary and its required help before producing a distributable ZIP.
2. **5.3 — OEM help is absent.** [Build-Package.ps1](../powershell/packaging/Build-Package.ps1) substitutes module name, prefix, publisher and description. It never emits brand-specific command help or uses `helpUri`; [Module.psm1](../powershell/module/Module.psm1) only checks CLI version. AC #3 remains unmet.
3. **6.3 — migration report does not meet AC #1–2.** [Assess-Migration.ps1](../powershell/migration/Assess-Migration.ps1) assigns every changed pair `ChangedLines = 1` and emits no aggregate metrics. The 12 JSON pairs contain only `before`/`after`. Add per-case supported behavior, change locations/reasons and a summary that separates synthetic checks from customer results.
4. **6.4 — acceptance evidence is not yet traceable to the current source.** [acceptance-checklist.md](../powershell/release/acceptance-checklist.md) reports Windows and live runs, but omits exact build identity and resource/cleanup records, including the unresolved temporary-account outcome recorded in story 6.4. Keep the published conclusion at no-go until the evidence record and customer/brand gates are explicit.
