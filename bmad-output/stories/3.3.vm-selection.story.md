# 3.3: 为写操作解析唯一资源与原连接

**Story ID:** 3.3
**Epic:** 3 — VM 查询与对象
**Slug:** vm-selection
**Status:** review

> 单次开发会话范围（约2–8小时）；本文件仅规划。前置依赖完成后实施，不包含真实云操作或发布。

## Story

As a **多环境管理员**, I want **在写操作前得到确定的 UUID 和连接**, so that **避免同名资源或默认环境变化导致误操作**。

## Acceptance Criteria

<!-- LOCKED：外部开发工具不得修改。 -->

1. 给定 VM 对象或显式 Name/Id 选择器，当解析写目标时，则从 registry 校验 BrandId、ConnectionId、Generation，再在该连接核对 UUID；不能使用对象提供的 ConfigPath/Server 替代 registry 路由。
2. 给定一个名称匹配多台 VM、对象已断开、跨品牌对象或旧 generation，当解析时，则产生确定的歧义/连接错误且写请求数为零；显式传入多个合法 VM 对象时分别解析，不自动扩大为同名批量。
3. 给定用户修改公共属性、反序列化对象或显式 Server 与对象所属连接冲突，当解析时，则拒绝冲突/无法验证身份的输入，不回退用户默认 context；只有有效 registry 身份和服务端 UUID 核对通过的目标可交给 mutation 层。

## Tasks / Subtasks

- [ ] 实现以 registry 为权威的目标解析 (AC: #1)
- [ ] 实现名称唯一性和断开/品牌/generation 保护 (AC: #2)
- [ ] 实现对象及 Server 冲突校验 (AC: #3)

## Testing

**Approach:** 开发阶段采用 Pester 单元或本地集成测试，CLI/云调用使用合成 stub；不包含真实凭据。

- AC #1 → 以两个不同 endpoint 的同 UUID fixture 检查实际路由只来自 registry。
- AC #2 → 模拟重名、失效、跨品牌和旧 generation，断言零写请求。

**Fixtures / mocks:** 本故事 Owned Scope 下的合成资源与stub，复用已有process/registry测试工具；不保存敏感服务端响应。
