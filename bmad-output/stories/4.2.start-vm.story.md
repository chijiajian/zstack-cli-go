# 4.2: 用原生对象管道启动并等待 VM

**Story ID:** 4.2
**Epic:** 4 — 启动与兼容入口
**Slug:** start-vm
**Status:** review

> 单次开发会话范围（约2–8小时）；本文件仅规划。前置依赖完成后实施，不包含真实云操作或发布。

## Story

As a **从 VMware 迁移的管理员**, I want **将查询对象管道传给启动命令并得到已运行对象**, so that **保留批量启动脚本结构且准确判断结果**。

## Acceptance Criteria

<!-- LOCKED：外部开发工具不得修改。 -->

1. 给定已停止的合法对象、Id 或唯一 Name，当调用拟议 Start-<Prefix>VM 时，则通过目标解析和 ShouldProcess 后逐 UUID 串行调用 CLI start 的纯 JSON 契约；不把名称直接交给 CLI 同名批量路径。
2. 给定启动已提交但 VM 尚未 Running，当调用默认启动模式时，则复用 4.3 等待直到 Running，刷新并输出 VM；默认总 deadline 为300秒，含启动进程与轮询。已运行目标返回当前 VM，不宣称重新启动；其他不适用状态返回冲突。
3. 给定部分失败、非法响应、超时或取消，当处理结果时，则结合退出码与逐项 status，尊重 ErrorAction；写结果无法确定时标记 OutcomeUnknown 并携带安全目标引用，不自动重试写或宣称回滚。
4. 给定 -RunAsync、-Kill 或 VMware 专属类型对象，当绑定/验证时，则本地拒绝，不伪造 Task，也不忽略参数；WhatIf/Confirm 行为继承 4.1。

## Dev Agent Record

- 2026-11-09 — Start calls strict UUID mode and uses the shared deadline for waiting. The loopback fixture reached Running.
- 2026-11-10 — 修复 CLI 启动请求仍受默认 120 秒限制的问题。模块把 300 秒总时限中的剩余预算传给 CLI 请求和子进程，随后沿用同一时限等待并刷新。回归使用两次异步作业轮询并检查实际传参，无需让测试等待两分钟。
- 2026-11-10 — Windows 11 Enterprise LTSC x64 上的 PowerShell 7.4.20 和 7.6.6 均通过异步启动的超时传递、作业轮询和状态刷新断言，使用内置 Windows CLI 和来宾 loopback 模拟 API。
- 2026-11-10 — 0.1.2 从 Windows 原生 PowerShell 7.6.6 启动两台专用临时 VM。账户密码和 AK/SK 各完成 `Stopped → Running`，控制端按 UUID 独立验证。cloud 返回管理节点 IP 形式的异步回调，CLI 核对连接对端后沿原配置地址轮询。
